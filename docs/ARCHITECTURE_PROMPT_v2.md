# Промт: проектирование production-grade системы удалённого администрирования Windows (полный редизайн с нуля)

## 0. Роль и задача

Ты — Senior Windows Systems Architect и эксперт по сетевым системам реального времени (продукты класса AnyDesk / TeamViewer / RustDesk): low-latency захват экрана (DXGI Desktop Duplication), инъекция ввода (Win32 SendInput), Windows-службы и Session 0, NAT traversal (ICE/STUN/TURN), end-to-end шифрование (Noise, libsodium), бинарные протоколы и схемы данных, code signing и enterprise-развёртывание.

Задача: **полный проектный документ** для переписывания существующей системы с нуля — выбор языка и стека, архитектура, roadmap, threat model, инструментарий. **Production-код не писать.** Допустимы только дизайн-артефакты: фрагменты схем (.proto-эскизы), псевдокод интерфейсов — с пометкой. Язык ответа — русский; имена API и технологий — по-английски.

## 1. Продукт и конечная цель

Легитимная система удалённого администрирования для IT-отделов и техподдержки парка подконтрольных Windows-машин (включая кассовые/POS-узлы). Оператор (viewer) подключается к управляемой машине (agent): рабочий стол, ввод, файлы, терминал, процессы, реестр.

- Клиенты: только Windows 10/11 x64 (Windows 7/8 и ARM64 не нужны; Linux/macOS-клиенты — вне скоупа v1).
- Серверная часть (signaling/relay): допустим Linux/Docker, self-hosted.
- Распространение: подписанный инсталлятор, централизованный роллаут (MSI/GPO/Intune), автообновление.
- Ожидаемый результат — документ, по которому можно сразу начинать реализацию.

## 2. Контекст: legacy, который переписываем

Есть рабочая legacy-реализация на Python (Tkinter + ctypes + dxcam; relay на голом TCP; исходники доступны как проект ratPy — при наличии доступа сверяйся). Аудит это подтвердил — повторять данные ошибки запрещено:

1) pickle.loads() на сетевых данных — RCE.
2) Нет шифрования и аутентификации транспорта (голый TCP через публичный relay).
3) 6-значный session/device ID — брутфорсится.
4) Файлы передаются base64 в JSON (оверхед 33%, весь файл в памяти, нет докачки).
5) Монолитные файлы 1000–2400 строк; глобальный синглтон shared_metrics (set_/get_ на 20+ полей).
6) Polling вместо событий: clipboard (sleep-цикл), hotkeys (GetAsyncKeyState в цикле).
7) UAC-elevation при каждом запуске.
8) Захардкоженный relay; один сервер без failover.

## 3. Что сохраняем из legacy (концепции проверены боем; реализацию улучшить)

1. Топология client–server–relay: оба конца ходят исходящим TCP к relay, pairing по session_id — пробивает любой NAT. Добавить P2P-приоритет (ICE/STUN) и relay-fallback.
2. Захват экрана через DXGI Desktop Duplication — единственный основной путь; GDI/BitBlt — только фолбэк для headless/Session 0.
3. Tile-based delta (тайлы 64×64, xxhash; отправка только изменённых) — сохранить как фолбэк; целевое — аппаратный видеокодек H.264/AV1 (NVENC/AMF/QSV) с dirty-rects.
4. Бинарный протокол с типами пакетов и явным кадрированием ([1B тип][4B длина BE]) — идею сохранить, payload перевести на версионированные схемы.
5. Асинхронный RPC с request_id поверх мультиплексированного стрима (файлы, мониторы, clipboard) — сохранить паттерн.
6. Адаптивное качество по backpressure (пропуск кадров → снижение качества → восстановление) — сохранить, добавить гистерезис.
7. Модальное подтверждение входящего подключения («Разрешить / Отклонить / Разрешать автоматически от этого клиента») — сохранить.
8. Single-instance через named mutex — сохранить.
9. Hardware-based device ID — SHA256(серийник диска + плата + имя ПК) — сохранить; расширить с 6 цифр до 9–12 символов base32.

## 4. Hard mandates (не обсуждаются)

4.1 **Десериализация.** Запрещены pickle/marshal/shelve, yaml.load() без SafeLoader, Java ObjectInputStream, .NET BinaryFormatter, любой механизм восстановления произвольных типов. Разрешены только schema-based форматы: Protobuf / Cap'n Proto / FlatBuffers / MessagePack (с whitelist типов); JSON — только для простых текстовых полей. Все сообщения — явная версионированная схема, компилируемая на обеих сторонах. Также запрещены eval/exec по данным из сети.

4.2 **Сквозное шифрование (relay не видит payload).** Требуется одна непротиворечивая схема, без «или». Для каждого плеча (viewer↔relay, agent↔relay, P2P-канал) укажи: протокол, аутентификацию сторон, происхождение ключей, и что может/не может скомпрометированный relay. Гипотеза по умолчанию (принять или аргументированно опровергнуть): транспорт — QUIC + TLS 1.3 (mTLS для служебного канала); E2E payload — Noise_XX (или libsodium secretstream) поверх транспорта; relay пересылает непрозрачные байты. Собственная криптография запрещена — только проверенные реализации (Noise, libsodium, ring/rustls, OpenSSL).

4.3 **Аутентификация и анти-брутфорс.** Долговременные Ed25519-ключи на машину; TOFU-pinning на viewer с явным диалогом; одноразовый PIN на сессию (TTL, малый лимит попыток), участвующий в PAKE-обмене (например, SPAKE2), а не «сравниваемый» по сети. Лимиты попыток — на трёх уровнях (сессия / агент / глобально) с эскалацией блокировок. Хранение ключей на диске — защищённое (DPAPI machine-scope и/или TPM) — реши и обоснуй.

4.4 **Авторизация (не только аутентификация).** Терминал/ФС/реестр дают полный контроль над агентом; компрометация viewer = контроль над парком (особенно при auto-allow). Обязательны: гранулярные права клиентов (scopes), per-agent ACL, журнал действий, отзыв ключей/устройств, опциональная запись сессий. В threat model обязательно — сценарий «скомпрометированный viewer».

4.5 **Легитимность.** Никаких скрытых режимов, backdoor, обхода UAC/AV, persistence вне официального инсталлятора. Подключение — только по явному согласию пользователя управляемой машины (модальный диалог); auto-allow — политика пользователя; журналирование подключений.

4.6 **AV-совместимость честным путём.** Code signing (EV-сертификат или Azure Trusted Signing), подпись SHA-256 + RFC 3161 timestamp (SHA-1 не использовать), submission в Microsoft и топ-3 AV-вендоров, накопление репутации. Никаких упаковщиков/обфускации/evasion.

4.7 **Гигиена кода и архитектуры.** Ни одного файла >400 строк (исключение — генерируемый код; оговорить); явные интерфейсы модулей (protocol / transport / codec / input / fs / ui); dependency injection вместо глобальных синглтонов; события вместо polling (clipboard — WM_CLIPBOARDUPDATE; hotkeys — RegisterHotKey или WH_KEYBOARD_LL); UAC — только для установки службы и действий, требующих admin; конфигурация вместо хардкода; для бинарных данных — chunked-стримы, не base64.

## 5. Требования MVP

### 5.1 Удалённый рабочий стол
- Захват: DXGI Desktop Duplication (основной путь); многомониторность (EnumDisplayMonitors + GetMonitorInfoW), переключение на лету.
- Кодек — решить в дизайне, не «потом»: базовая ставка — аппаратный H.264 (NVENC/AMF/QSV) с dirty rects и intra-refresh; tile-delta — фолбэк (headless, нет HW). Обоснуй, оцени матрицу железа и SW-фолбэк.
- Latency: цель ≤50 мс end-to-end при 1080p/30fps в LAN. Операционализируй: бюджет по стадиям (захват → энкод → сеть → декод → рендер) + методика измерения (что и чем меряем).
- Ввод: SendInput (не mouse_event/keybd_event); корректная работа с раскладками; курсор (GetCursorInfo + наложение).
- Адаптивное качество (см. §3.6).
- До логина / secure desktop: явно решить и описать — (а) поддержка pre-login-экрана и Ctrl+Alt+Del (SAS; например SendSAS, работа с Winlogon-десктопом) либо (б) обоснованное исключение из v1. Пункт не считается раскрытым без явного решения.

### 5.2 Агент
- Windows-служба (SCM: CreateService / StartServiceCtrlDispatcher), Session 0.
- Session helper в интерактивной сессии (WTSQueryUserToken + CreateProcessAsUserW); связь service ↔ helper через named pipe. Обработать: смену сессий, fast user switching, несколько одновременных сессий (в т.ч. RDP на управляемой машине) — что поддерживается, что нет.
- Установка/удаление инсталлятором; автозапуск; silent install для централизованного развёртывания.
- Автообновление — обязательная подсистема: подписанные манифесты, staged rollout, откат, самообновление службы; отдельная фаза roadmap.

### 5.3 Сеть
- NAT traversal: STUN (RFC 5389/8489), ICE candidate gathering; P2P-приоритет (UDP); relay-fallback (TURN-совместимый).
- Мультиплексирование потоков (видео / ввод / файлы / control) в одном соединении с приоритетами. Зафиксировать транспорт: QUIC или собственный mux поверх TLS/TCP — выбрать и обосновать. SCTP не использовать (нет поддержки в Windows на уровне ОС).
- Решить и обосновать: ICE пишем сами или берём готовый стек (libdatachannel / Pion / str0m и т.п.) — это влияет на выбор языка; укажи следствия.
- Signaling: WebSocket/QUIC; обмен SDP/ICE-кандидатами; аутентификация устройств.
- Несколько relay с failover; адреса — из конфига.

### 5.4 Функции
- Файлы: двухпанельный менеджер (TC-style); chunked binary transfer; checksum блоков (xxh128 или SHA-256); докачка, прогресс, отмена; защита от path traversal / symlink-атак.
- Терминал: CMD и PowerShell через ConPTY (ANSI, интерактивность).
- Процессы: EnumProcesses / OpenProcess / GetModuleBaseName / GetProcessMemoryInfo.
- Реестр: read-only в MVP (RegOpenKeyEx / RegEnumKeyEx / RegQueryValueEx).
- Clipboard: событийно (WM_CLIPBOARDUPDATE), текст + CF_HDROP; отдельно продумать политику (что синхронизируем, как защищаем).
- Индикация: трей / статус активной сессии на управляемой машине; журнал всех подключений.

### 5.5 Безопасность (сверх §4)
- STRIDE по компонентам, ≥5 угроз с митигациями; обязательно покрыть: malicious relay, compromised viewer, replay, DoS signaling/handshake, supply chain зависимостей, подмена канала обновлений, локальный EoP.
- Явные trust boundaries и что каждая граница защищает.

## 6. Ограничения и non-goals

- Клиенты — только Windows 10/11 x64; relay/signaling — могут быть Linux.
- UI клиента — только нативный (WPF / WinUI 3 / Qt / Flutter Desktop — выбрать и обосновать). Web/Electron/Tauri — нельзя. Служебные API и панель relay — допустимы (решить отдельно).
- Запрещено: готовые RDP-библиотеки; REST/HTTP в data-path agent↔viewer (только бинарный протокол); Python в production.
- Лицензионная чистота обязательна: по каждому крупному компоненту (кодеки, FFmpeg, x264, crypto, UI) — лицензия и риски (LGPL/GPL-ловушки, патенты H.264); приоритет — permissive (MIT/Apache/BSD); GPL/платные — только с явным обоснованием и оценкой стоимости.
- Non-goals v1 — зафиксировать списком (минимум обсудить): аудио, мобильные и кроссплатформенные клиенты, VPN, печать, web-клиент, продвинутое управление парком.

## 7. Формат ответа

1. **Язык и стек.** Сравнение Rust / C++23 / C# (.NET 8+) / Go по критериям: (a) Win32 interop; (b) zero-overhead для real-time; (c) memory safety; (d) async и сеть; (e) экосистема crypto/codec; (f) сборка, подпись, CI; (g) долгосрочная поддержка. Финальная рекомендация. Split допустим (например, C# для UI + Rust для ядра) — с обоснованием и планом совместимости (общая схема протокола, общий crypto-слой, interop). Для выбранного стека — конкретные библиотеки по подсистемам: capture / codec / network / crypto / input / fs / service / ui / update — с лицензиями и «почему не альтернатива».
2. **Инструменты.** IDE; сборка; отладка (WinDbg, ETW, WPR); profiling (Tracy/VTune/WPA); CI/CD (шаги: lint → test → build → sign → package → release; SBOM и аудит зависимостей); инсталлятор (WiX vs Inno Setup — обосновать); signing workflow (тип сертификата, HSM / Azure Trusted Signing); enterprise-деплой (MSI/GPO/Intune).
3. **Архитектура.** Mermaid-диаграмма компонентов: Viewer UI ↔ Viewer Core ↔ Signaling ↔ Relay ↔ Agent Service ↔ Session Helper. Ответственности и интерфейсы; схема процессов (Session 0 vs пользовательская сессия); потоки и приоритеты; таблица крипто-слоёв по плечам; диаграмма состояний соединения с таймаутами; latency-бюджет; эскиз схемы протокола (.proto-фрагмент допустим).
4. **Roadmap.** Фазы: цели, deliverables, критерии выхода, зависимости, риски; длительность — диапазонами («2–4 недели») с допущениями; внешние lead time (сертификат подписи, AV-whitelisting) учтены; тест-стратегия в фазах (unit / integration / soak; fuzzing протокола — с фазы протокола; матрица: версии Windows, AV, железо для кодеков); отдельная фаза — автообновление.
5. **Ключевые API** — ≥30 функций/интерфейсов по подсистемам с назначением (DXGI, SendInput, SCM, WTS/Session 0, SendSAS, multi-monitor, network, clipboard, hardware ID, named pipe, ConPTY, processes/registry и т.д.).
6. **Threat model** — STRIDE по компонентам, ≥5 угроз и митигации, trust boundaries (§5.5).
7. **Риски, допущения, открытые вопросы** — что осталось нерешённым и требует моего решения (списком).
8. **Decision log** — ключевые развилки: что выбрано и почему отвергнуты альтернативы.

## 8. Стоп-лист

- Не писать production-код (фрагменты схем/интерфейсов — можно, с пометками).
- Не предлагать: кроссплатформенные клиенты; web-UI клиента; RDP-библиотеки; REST в data-path; Python в production; SCTP; SHA-1-подписи; скрытые режимы и evasion; самодельную криптографию.
- Не оставлять неоднозначностей: где есть выбор — принять решение и обосновать (исключение — пункты, явно вынесенные в «открытые вопросы»).
